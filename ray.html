The hard part

Trust is architecture, not tone.

Every answer runs the same path. The model never reaches data directly, and it never acts on its own.

  1. Question
    Someone asks in the portal, inside a project or across the process knowledge.
  2. Viewer-scoped tools
    Ray reaches only for tools the current viewer is already allowed to use.
  3. Live data or published knowledge
    Tools read real project state, or the published help-center articles.
  4. Grounded answer or proposal
    Ray answers with sources, or proposes an action. Never both silently.
  5. Explicit confirmation
    A proposal waits. The person confirms before anything happens.
  6. Existing guarded operation
    Confirmed work runs through the portal's own guarded operation, not a new path.

Invariants, always on

Reauthorize every project-bound turn.

Cite only sources that actually ran.

No source means "I could not verify that."

A proposal is not execution.

Confirm rechecks visibility and capability.

Sensitive and destructive actions stay out of the catalog.

Product decisions

Three choices that shaped Ray.

Not a feature list. The calls that decided how it should feel to trust an assistant with real work.

Decision 01

Stay in context

The answer is worth less if you have to leave the project to get it. Ray ships as a persistent drawer and a pop-out, and its turns run server-side so they survive navigation. You can move around the portal and the work Ray is doing does not fall on the floor.

Decision 02

Narrate the work

A silent spinner asks for blind trust. Instead Ray shows the actual tool step in plain language while the avatar moves, then comes to rest on a settled answer with its sources and freshness. You watch the reasoning happen, so you can judge the result.

Decision 03

Escalate honestly

When project data and knowledge cannot explain the issue, the right move is a person, not a confident guess. Ray hands off to human support, with deduplication and rate limits so one problem does not turn into a pile of tickets.

The lesson

Usefulness was the easy half.

Getting an assistant to say something helpful is not hard anymore. The hard part was everything around the answer. Permission, so it only ever sees what the viewer sees. Grounding, so every claim points at a source that actually ran. Action boundaries, so it can propose but never quietly execute. And graceful escalation, so it knows when to stop and hand the problem to a person.

Ray started from the team's shared chat foundation. My work was turning that into something the portal could trust with real projects, on the surfaces where the work already happens. That is the part I am proud of.
